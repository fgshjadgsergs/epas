# Machine values калькуляторов: регистр и совместимость

## Правило

1. **Имена GET-параметров** — строго нижний регистр, слова через дефис
   (`format`, `paper`, `qty`) — ТЗ §15.16. Ключи `customW`/`customH` из
   раннего прототипа заменены на `w`/`h`.
2. **Канонические machine values** задаются backend definition
   (`CalculatorOption.value`) и считаются регистрозависимыми строками.
   Для исторических форматов листов канон — как в примере ТЗ §15.16
   (`/listovki/?format=A5&…`): `A4`, `A5`, `A6`, `DL`. Для всех остальных
   значений канон — нижний регистр в kebab-case (`coated-150`,
   `matte-lam`, `4+4`, `custom`).
3. **Новые параметры и опции** создаются только в нижнем kebab-case;
   верхний регистр форматов — закреплённое ТЗ исключение, а не образец.

## Legacy-совместимость

URL со значением в «неправильном» регистре (`?format=a4`) не ломается:
`parseUrlState` сопоставляет значение с канонским без учёта регистра,
подставляет каноническое (`A4`) и помечает ключ на нормализацию — адрес
переписывается через `replaceState` (без новой записи истории, без
повторного pushState и без дублирования аналитики/hit).

Массовая миграция канона `A4 → a4` сознательно НЕ выполнена: значения уже
используются в опубликованных demo-definition, registry-preset'ах и
примерах ТЗ; смена канона потребовала бы новой версии definition и
редиректов старых ссылок. Если заказчик подтвердит требование нижнего
регистра для значений — это отдельный техдолг: новая версия definition с
lowercase-опциями + приём старых значений через тот же case-insensitive
слой.
